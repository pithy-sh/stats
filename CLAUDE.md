# Pithy Stats — coding rules

Download, release and repo stats for the Pithy kit, served as JSON to the `/stats/` page on pithy.sh. **Public, MIT.** Anyone can read this code, so nothing in it is a secret and nothing secret goes in it.

It is **a Pithy app**, built on the kit it measures, exactly as an adopter would build one. Every DX gap hit here is a bug in the kit: file it at `pithy-sh/pithy` through `/fix-kit`, and never work around it silently.

## The shape

- **One Worker, `apps/api`.** No UI. A Hono router composed by `createEntrypoint` serves the JSON API.
- **A daily Workflow does all the collecting.** A cron on its spec starts it at 02:00 UTC; it runs the fetches as steps, writes D1, then builds the JSON and writes it to R2. The spec's `instanceId` names a cron start by the UTC day it was scheduled for, so a second cron start that day is logged as already started, not run, and names a manual trigger without an id `manual-<UTC time to the millisecond>`, never a bare day, so it never takes the day's cron slot; rows are keyed by the UTC day they were captured as well, so two runs on one day under different ids still leave one set of rows. It stays triggerable by hand for backfills: `bun run pithy workflow trigger api/collect --env <env> --params '<json>' [--id <id>]`, where an id already taken is refused; a failed run's error names the refill command (`refillCommand` in `collect/workflow.ts`) under `refill-<day>-<failure time>`, a fresh id for each failure, so a refill that fails never prints its own id back. Daily downloads re-fetch the last three days, or from the day after the newest day held when that is earlier, so days a capped or failed run skipped are caught up, except for a package no run has yet collected in full: a `download windows` step, before any package's version-downloads or daily-downloads step, gives it the days from its registry creation date (no further back than npm's eighteen months) and journals that choice, and the package stays pending (`packages.history_collected_on` null) until one of its steps writes them, so a package that arrives with history, or a first run that fails, loses no day. That same step asks npm which day it last finished counting (`/downloads/point/last-day` and `/point/last-week`, for one package, through the paced client), refuses an answer whose `last-week` is not the seven days ending its `last-day` or whose `last-day` has not ended, records the day in `npm_days`, and ends every window there, so a day npm has not counted is never stored; if the step fails, neither version nor daily downloads are fetched that run. Version downloads run straight after it, and their completion step asks npm for `last-week` again: only if it has not moved is that week recorded in `npm_days` as the one the day's per-version counts cover; if it has, the day's week is cleared, since its counts may now cover two weeks. Two runs on one day may overlap, so `npm_days.last_day` only moves forward, and a second run's `download windows` step keeps a week already recorded that ends on the day the row names, clearing it only when npm names a later day, whose counts the run then rewrites. A run that finds a week recorded asks npm for `last-week` again before writing each package's per-version counts, and clears that week if npm has moved past it; a completion step that finds npm moved clears the week only while the row still names the day that run was told of, so a stale run never undates the week a newer run confirmed; a completion step that records a week asks npm for `last-week` once more after writing it, and clears that week if npm has moved since, so counts another run fetched after npm closed a day are never dated by it. A publish in between dates the day's counts, or falls back to the newest dated capture before them. The publish step takes `asOf` as the newest day held no later than npm's newest answer, and publishes in `versionWeeks` only captures with a recorded week, dated by it; a capture without one, those from before `npm_days` existed included, is kept in D1 but never published.
- **D1 is internal to the Workflow.** It holds the history: one row per package per day, and the snapshots npm forgets (per-version counts keep seven days upstream). No request handler reads D1, and `apps/api/src/noRequestReadsD1.test.ts` fails if a module outside `collect/`, `data/` and `migrations/` names the app database.
- **R2 holds what is served.** Each run ends with a publish step that builds `summary.json` and `latest.json` from D1 (`collect/publish/`) and writes each with a dated snapshot. The routes in `serve/` answer each file from the edge cache, keyed by path alone, or on a miss from one R2 read that they then keep at the edge; the JSON's shape lives in `contract/stats.ts`.
- **One clock: the cron.** `COLLECT_CRON` lives in `apps/api/src/schedule.ts`, which imports nothing from `collect/`, so the serve path reads it without loading collector code. The run start is read off it, and only a daily `M H * * *` schedule is accepted (`dailyRunStart` throws on any other, and a test holds `COLLECT_CRON` to it). A run's files are taken to be ready `READY_AFTER_MINUTES` after it starts: a Worker var declared with the kit's `defineVars` in `apps/api/src/vars.ts` (schema, default 15, and a value for staging and prod, `15` in each today, though they may differ) and set as `vars` in `apps/api/pithy.config.ts`. `bun run pithy worker sync` writes it into every `vars` block of `wrangler.jsonc`, `pithy doctor` names a stanza that drops it or holds a value its schema refuses, and the Worker reads it with `VARS.read(env)`. A value set as text is taken only as a plain decimal, so `"20"` and `"15.0"` read as 20 and 15 while `" 15"`, `"15 "`, `"1e1"`, `"0x10"` and `""` fall back; `vars.test.ts` pins that. A missing, non-integer, negative or 24-hours-or-more value falls back to 15 and is logged once per value per isolate, from the `onFallback` that `VARS.read` calls; it never fails a request. The cache functions take the schedule as input, and the publish step writes `nextUpdate`, the time the first run after `generatedAt` is ready, into both files and their snapshots. Prose names the rule ("15 minutes after the 02:00 UTC run starts, by default"), never a clock time; the route and contract descriptions build it from `READY_RULE`.
- **Caching is computed per request.** `Cache-Control: max-age` is the seconds from now until the next ready time, plus `stale-while-revalidate`, so every copy expires when the next file is ready; once a ready time has passed and the current file was uploaded before that run started, the run is late and a copy is kept five minutes. A dated snapshot expires at the next ready time or at midnight UTC, whichever is sooner, with no stale window, until its day is over, and is immutable from then on; an edge copy taken during the day is never served as immutable, so the first immutable answer is a fresh R2 read. A run that publishes after its day never rewrites an existing snapshot, and a 404 is cached for five minutes. The R2 object's ETag answers `If-None-Match` with a 304, and a malformed `If-None-Match` is ignored. Query strings are ignored, so they cannot bust anything.
- **Upstreams see the Workflow once a day, never a visitor.** npm, the npm registry, GitHub, jsDelivr, deps.dev. Every request goes through `collect/upstream/client.ts`: npm's downloads API is paced (`NPM_API_GAP_MS`, with its measured basis), and a rate-limited answer from any upstream is retried in place before it becomes an `UpstreamError`. A source about packages runs one step per package, named `<source> <package>`, then a step named for the source that records it complete; a failing step logs its error's detail through the kit's Worker logger.
- **Upstream tokens live in the Secrets Store.** Each is declared in `apps/api/src/secret/registry.ts`, set with `bun run pithy secrets create <name>` (`--env <env>` only for one declared `scope: "environment"`), and read with `secretsStore` inside the step that uses it, never returned from a step or logged. Today there is one, `github-token`, declared `scope: "global"`: one entry, `stats-global-github-token`, bound by every environment.

## Toolchain

Bun for everything (`bun install`, `bun run`, `bunx`), never npm or npx. A runtime dependency belongs to the app that imports it, in `apps/api/package.json`; the root holds only devDependencies, and `@pithy-sh/secrets` is one of them as well as a runtime dependency of `apps/api`, because the root `vitest.workers.config.ts` imports `devEncryptionKeys` from it; `pithy add secrets` declares it there, and `pithy doctor` names a root import a clean install cannot resolve. A Workflow test that holds a step while a second run interleaves uses `createGate` from `@pithy-sh/core/testing`. Biome for lint and format. Vitest, with the Workers pool for anything touching D1, R2 or a Workflow. ESM only, TypeScript strict. Every module must load under Node's type stripping, because the `pithy` CLI loads `pithy.config.ts` and everything it imports that way: no parameter properties, no enums, nothing else that needs a transform. The `no-unerasable-syntax` safeguard in `plugins/`, registered in `biome.jsonc`, fails `bunx biome check .` on that syntax in `apps/*/src` and any `pithy.config.ts` (`apps/api/src/lintSafeguards.test.ts` holds it to that), and `apps/api/src/typeStripping.test.ts` runs Node's own stripper over every module and fails on any that does not strip.

## Gates

```bash
bun run typecheck
bunx biome check .
bun run test
```

CI runs the same three after `bun install --frozen-lockfile`, on every pull request and every push to `main` (`.github/workflows/ci.yml`), with `bun run pithy setup --skip-install` and `bun run pithy doctor --offline` between typecheck and test, and no Cloudflare credentials, so a `wrangler.jsonc` stanza that drops a declared var, or holds a value its schema refuses, fails CI. Setup is there because doctor fails on a dev database with pending migrations, and a fresh checkout has none applied.
